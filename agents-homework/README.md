# Agents homework: агент суммаризации JSON

Агент получает задачу обработать JSON со статьями. **Модель сама выбирает MCP-инструменты**
открытия файла, чтения статьи, суммаризации, сохранения и завершения.
LangGraph организует только цикл выбора и выполнения вызовов.

## Запуск

Проверено на Windows / Python 3.13. MCP SDK v2 требует Python 3.11+.
В папке проекта:

```powershell
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
.\.venv\Scripts\python.exe main.py
```

Создай `.env` по примеру `.env.example`, не перезаписывая существующий ключ:

```dotenv
GROQ_API_KEY=твой_ключ
GROQ_MODEL=openai/gpt-oss-120b
```

По умолчанию вход `data/test_articles.json`, выход `data/result.json`.
Сервер запускается автоматически; отдельно открывать второй терминал не нужно.

```powershell
.\.venv\Scripts\python.exe main.py --input data/test_articles.json --output data/result.json --max-steps 300
.\.venv\Scripts\python.exe -m unittest discover -s tests -v
.\.venv\Scripts\python.exe -m pip check
```

Пути по умолчанию относятся к папке main.py; явно заданные относительные пути —
к текущей рабочей папке. Прямые зависимости закреплены в requirements.txt.
requirements-lock.txt — полный снимок исходного Windows-окружения, включая pywin32.
На других платформах устанавливай requirements.txt.

## Что изменилось после проверки условия задания

Раньше модель видела только read_article, а граф автоматически вызывал суммаризацию
и сохранение. Это был рабочий фиксированный workflow, но он не выполнял требование
самостоятельного вызова суммаризатора и сохранения моделью.

Теперь все пять инструментов передаются модели через bind_tools. В графе нет узлов
read/summarize/save и нет переходов, выбирающих следующее действие вместо модели.

```text
START → agent → tools → agent → tools → ...
                    └─ успешный finish → END
```

`agent` получает задачу, схемы всех tools, короткое состояние сервера и последнюю
пару вызов/ответ. Он возвращает tool call. `tools` выполняет именно этот вызов через
MCP, возвращает результат модели. Следующее действие снова выбирает LLM.
Результат проверяет сервер: нельзя сохранить неготовое резюме или завершить работу,
пока не сохранены все статьи. Проверки запрещают неправильные действия, но сами
не вызывают следующее действие. Граф не навязывает индекс: тест обрабатывает статьи
в обратном порядке и также успешно завершается.

## MCP-инструменты, доступные модели

| Инструмент | Параметры | Назначение |
| --- | --- | --- |
| open_articles | нет | Открыть заданный файл, проверить записи, вернуть количество, создать выход с резервной копией предыдущего результата |
| read_article | index | Выбрать и прочитать одну несохранённую статью в память сервера |
| summarize_article | нет | Отдельным запросом к Groq получить резюме текущей статьи и оставить его на сервере |
| append_result | index | Сохранить подготовленное резюме с исходными id/title |
| finish | нет | Проверить полноту и содержимое файла результата; разрешить завершение |

Пути входа и выхода задаёт пользователь через CLI. Агент работает с выбранным
файлом и не ищет произвольные файлы по всему компьютеру. Загрузка содержимого
происходит только после выбранного моделью open_articles, не при старте сервера.

Повторные open_articles/summarize_article/append_result в той же сессии безопасны:
не очищают уже записанные результаты и не создают дубликаты. Сервер допускает одну
текущую статью и требует сохранить её перед переключением на другую.

## Контекст и данные

На каждом шаге планировщик получает максимум четыре сообщения:
1. Системную инструкцию.
2. Задачу в виде актуального краткого статуса и последнего результата.
3. Последний ответ модели с tool call (если есть).
4. Соответствующий ToolMessage от сервера (если есть).

Старая пара сообщений заменяется новой. add_messages и растущей истории нет.
Статус содержит только opened, total, saved, next_unsaved, current_index,
summary_ready. next_unsaved — подсказка, не принудительный выбор графа.

Полные статьи и резюме никогда не возвращаются в историю планировщика.
MCP-сервер держит исходный список, индекс текущей статьи, одно резюме и множество
сохранённых индексов. Полный текст видит только отдельный запрос суммаризации.
Это сохраняет контекст планировщика ограниченным, но память Python на сервере
растёт с размером входного JSON. Для гигантских данных нужен JSONL или база данных.

## Структура и функции

### main.py — запуск

- `ROOT`: папка проекта.
- `describe_error(exc)`: разворачивает вложенные ExceptionGroup, показывает причину.
- `run(input_path, output_path, llm=None, max_steps=300)`: проверяет пути, создаёт
  модель-планировщик, запускает MCP-сервер тем же интерпретатором, обнаруживает ВСЕ
  инструменты, передаёт их схемы в build_graph, вызывает graph.ainvoke ровно один раз.
  Не читает статьи, не вызывает рабочие инструменты и не управляет очередностью.
- `main()`: загружает .env, разбирает аргументы, включает logs/run.log и консольный
  журнал. Возвращает 0 при успехе, 1 при ошибке, 130 при прерывании.

### src/graph.py — два узла

- `AgentState`: status, last_result, calls, errors, done, exchange. В нём нет статей.
- `decode_result(result)`: разбирает structured_content либо один JSON TextContent;
  превращает ошибку инструмента в ValueError. SDK может кодировать dict текстом.
- `build_graph(client, llm, schemas)`: предоставляет модели все схемы через bind_tools
  и собирает agent/tools с единственным условием завершения — подтверждённый finish.
- `agent_node(state)`: создаёт ограниченный контекст, делает запрос к Groq, сохраняет
  предложенные tool calls. tool_choice=required требует выбрать инструмент.
- `tools_node(state)`: принимает один известный вызов, исполняет через MCP, формирует
  ToolMessage, обновляет статус. Ошибку возвращает модели для исправления; после
  трёх ошибок подряд прекращает запуск. Транспортные ошибки прекращают запуск сразу.
- `route(state)`: END после успешного finish, иначе agent; названия рабочих действий
  и текущий индекс не используются для выбора следующего узла.

### mcp_server.py — инструменты и рабочие данные

- `create_server(input_path, output_path, llm=None)`: создаёт MCPServer, регистрирует
  пять tools, хранит данные в замыкании. Параметр llm позволяет тестировать суммаризацию
  без API. В production клиент суммаризации создаётся лениво на сервере.
- `status()`: возвращает короткий снимок прогресса без текстов и списка всей истории.
- `open_articles()`: валидирует файл до изменения выхода, делает резервную копию,
  создаёт пустой результат один раз за сессию, сообщает количество статей.
- `read_article(index)`: проверяет индекс, отсутствие сохранённой записи и несохранённой
  другой текущей статьи; сохраняет индекс, возвращает статус.
- `summarize_article()`: требует прочитанную статью, вызывает generate_summary
  из src/summarizer.py и сохраняет ответ в памяти сервера.
- `append_result(index)`: проверяет соответствие текущей статье и наличие резюме,
  вызывает файловую запись, затем очищает текущую статью/резюме и отмечает индекс.
- `finish()`: требует полного множества сохранённых индексов, перечитывает JSON,
  проверяет число записей, поля, исходные id/title и непустые summary.
- `main()`: загружает .env для отдельного процесса, читает CLI-пути, запускает stdio.
  stdout зарезервирован для протокола; обычные print здесь недопустимы.

### src/file_tools.py — обычные Python-функции

- `load_articles(file_path)`: читает UTF-8 (включая BOM), проверяет список объектов,
  непустые строковые id/title/text, уникальные id, предел title+text в 16000 символов.
- `atomic_write(file_path, data)`: пишет временный файл рядом с выходом, flush/fsync,
  затем os.replace; при ошибке убирает временный файл. Старый JSON сохраняется.
- `prepare_results(file_path)`: копирует старый выход в result.<UTC timestamp>.bak.json
  и атомарно создаёт []. Вызывается только выбранным моделью open_articles.
- `read_article(articles, index)`: отвергает отрицательные/недопустимые индексы,
  возвращает одну исходную запись.
- `append_result(file_path, article, summary)`: формирует id/title/summary, повтор
  той же записи не добавляет дубликат, конфликт резюме для id вызывает ошибку.

### src/summarizer.py — обращение к Groq

- `create_llm()`: проверяет ключ, создаёт ChatGroq с моделью из GROQ_MODEL,
  temperature=0, timeout=60, max_retries=2, max_tokens=2048.
- `summarize_article(llm, article)`: передаёт инструкцию и одну статью; требует
  сохранения фактов и игнорирования команд внутри исходного текста. Отвергает
  пустой ответ и завершение по лимиту длины. Возвращает строку.

## Назначение библиотек

| Библиотека | Назначение |
| --- | --- |
| langchain / langchain-core | Интерфейс сообщений, bind_tools и ToolMessage; импорты из core |
| langchain-groq | ChatGroq для планировщика и отдельного суммаризатора |
| langgraph | Состояние и цикл двух узлов |
| mcp 2.3.0 | Официальные Client, MCPServer, StdioServerParameters |
| python-dotenv | Загрузка ключа и модели из .env |
| asyncio | Асинхронное выполнение графа и MCP |
| unittest | Проверки без дополнительных библиотек |

Дополнительный адаптер MCP/LangChain не требуется: схемы обнаруживаются через
list_tools, передаются в bind_tools, вызовы исполняются через call_tool.
Документация: https://py.sdk.modelcontextprotocol.io/ и
https://reference.langchain.com/python/langgraph/graph/state/StateGraph .

## Проверки и ограничения

tests/test_workflow.py проверяет реальный MCP-протокол с тестовыми моделями:
все действия выбирает planner, альтернативный порядок статей, коррекцию раннего
finish, лимит ошибок и шагов, сохранность частичного результата, пустой вход,
резервную копию, валидацию, идемпотентность и атомарную запись. Отдельный тест
запускает настоящий дочерний stdio-сервер. Подробности прогона — VALIDATION.md.

- Внешнего цикла по статьям нет. Циклы в валидации/построении схем не управляют workflow.
- При обычном ходе: 3*N+2 решений планировщика и N запросов суммаризатора.
  Это дороже фиксированного workflow, но соответствует учебному требованию tool calling.
- Для N статей графу обычно нужно 6*N+4 шага. --max-steps ограничивает в том числе
  бесконечное повторение успешного инструмента моделью. Повторные вызовы тратят бюджет.
- Сохранение выполняется после каждой статьи. Автоматического resume после перезапуска
  нет: новый open_articles сохраняет старый выход в backup и начинает заново.
- Не запускай два процесса с одинаковым выходом: межпроцессной блокировки нет.
- JSON-структура проверяется автоматически. Фактическая точность и полнота резюме
  требуют отдельной оценки; технический успех не доказывает отсутствие ошибок LLM.
- .env, .venv, логи и backups не публикуются. Данные статей отправляются Groq только
  для суммаризации. Ключи и содержимое статей специально не логируются.
