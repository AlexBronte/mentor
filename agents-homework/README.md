# Agents homework: суммаризация статей

Рабочий агент на **Groq API + LangChain + LangGraph + MCP Python SDK 2.3.0**.
Читает статьи из JSON, обрабатывает по одной и сразу сохраняет результат.
Исходная структура проекта сохранена: main.py, src/graph.py,
src/file_tools.py, src/summarizer.py. Добавлены MCP-сервер, зависимости и тесты.

## Быстрый запуск в VS Code / Visual Studio

Открой папку проекта и терминал PowerShell. Используй интерпретатор
**.venv/Scripts/python.exe**. Активация окружения не обязательна:

```powershell
cd agents-homework
.\.venv\Scripts\python.exe main.py
```

По умолчанию вход — data/test_articles.json, выход — data/result.json.
Пути по умолчанию считаются от main.py, поэтому запуск возможен из другой папки.
Относительные пути, явно переданные в командной строке, считаются от текущей папки:

```powershell
.\.venv\Scripts\python.exe main.py --input data/test_articles.json --output data/result.json
```

MCP-сервер запускается и закрывается автоматически как дочерний процесс.
Вручную запускать второй терминал с сервером не нужно.

### Установка с нуля

Проверено на Windows и Python 3.13; SDK требует Python 3.11+.

```powershell
py -3.13 -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
.\.venv\Scripts\python.exe -m pip check
```

requirements.txt фиксирует прямые зависимости; requirements-lock.txt содержит
снимок всего проверенного окружения Windows/Python 3.13. Для точного повторения
этого окружения вместо requirements.txt можно установить requirements-lock.txt.
На других платформах используй requirements.txt: в полном снимке есть pywin32.

Создай .env по образцу .env.example, **не заменяя существующий рабочий .env**:

```dotenv
GROQ_API_KEY=твой_ключ_Groq
GROQ_MODEL=openai/gpt-oss-120b
```

Модель по умолчанию — openai/gpt-oss-120b. Нужна модель Groq с поддержкой
tool calling. Существующие переменные окружения имеют приоритет над .env.
Ключ не хранится в коде; .env исключён из Git.

## Формат данных

Вход — список объектов с непустыми строками id, title, text.
id должны быть уникальными. Дополнительные поля допустимы, но не используются.

```json
[
  {"id": "1", "title": "Пример", "text": "Полный текст статьи."}
]
```

Выход — список объектов, соответствующий порядку входных статей:

```json
[
  {"id": "1", "title": "Пример", "summary": "Краткое содержание."}
]
```

id и title копируются из исходника сервером, а не сочиняются моделью.
JSON сериализует Python: модель возвращает только текст резюме.
Русский текст сохраняется в UTF-8. Пустой вход создаёт [] без запросов к модели.

## Архитектура

```text
main.py
  └─ MCP Client → дочерний mcp_server.py (stdio)
       └─ обнаружение схемы read_article
  └─ один graph.ainvoke(...)
       START → initialize → agent → read → summarize → save
                              ↑                         │
                              └──── если есть статьи ──┘
                                                        └─ END
```

initialize получает количество статей и подготавливает выход через MCP.
agent вызывает Groq с описанием read_article, полученным от MCP-сервера.
Модель выдаёт tool call; граф проверяет, что выбран следующий ожидаемый индекс.
read исполняет этот вызов через MCP и кладёт статью в current_article.
summarize делает отдельный запрос к Groq с текущей статьёй.
save вызывает MCP append_result, проверяет число сохранённых записей,
очищает текущую статью и summary, увеличивает next_index.

Неверный выбор агента возвращает управление в agent максимум на три попытки.
Граф завершает работу только после сохранения всех статей.
Агент ограничен заданной последовательностью: он выбирает вызов инструмента,
а гарантии порядка и сохранения обеспечивает LangGraph. Это контролируемый
агентный workflow, а не агент со свободным планированием.

**Внешнего Python-цикла по статьям нет.** main вызывает граф один раз.
Цикл for в build_graph только регистрирует узлы; циклы в валидации проверяют
данные и не управляют обработкой статей.

### Почему контекст не растёт

У графа вообще нет накопительного поля messages или add_messages.
Каждое решение агента получает два свежих сообщения: системную инструкцию
и короткое состояние total / next_index / saved. Полные статьи туда не попадают.

Для суммаризации создаются ещё два свежих сообщения: инструкция и одна статья.
После сохранения current_article/current_summary очищаются.
Ответ MCP не добавляется в ToolMessage и не возвращается модели для планирования.
Нет незакрытых tool-call пар, потому что следующий вызов агента начинает новую историю.

Размер LLM-контекста зависит от одной статьи, а не от количества статей.
Для предсказуемости установлен предел 16000 символов на title + text:
слишком длинная статья вызывает явную ошибку до изменения результата,
а не незаметное усечение. Это ограничение по символам, не точный подсчёт токенов.
Разбиение больших документов на части здесь не реализовано.

MCP-сервер читает JSON один раз и держит исходный список в памяти Python.
Это **не** LLM-контекст. Для огромных файлов понадобится потоковый формат
(JSONL/БД); текущая версия рассчитана на домашний набор данных.

## Назначение библиотек

| Библиотека | Что делает в проекте |
| --- | --- |
| langchain / langchain-core | Экосистема LangChain; сообщения SystemMessage/HumanMessage, стандартная схема tool calling и bind_tools. Прямые импорты берутся из langchain-core. |
| langchain-groq | ChatGroq: запросы к Groq, привязка инструментов, таймаут и повторные попытки. |
| langgraph | StateGraph, состояние, узлы, условные переходы, обязательные шаги и завершение. |
| mcp 2.3.0 | Официальные MCPServer, Client, StdioServerParameters; реальный обмен с отдельным сервером. |
| python-dotenv | Загружает настройки из локального .env. |
| asyncio | Запускает асинхронный MCP-клиент и граф. |
| json, pathlib, tempfile, os | Чтение, проверка и атомарное сохранение файлов. |
| logging, argparse | Журнал выполнения и параметры запуска. |
| unittest | Автоматические проверки без отдельной тестовой зависимости. |

Дополнительный langchain-mcp-adapters не требуется: схема инструмента
обнаруживается через Client.list_tools(), передаётся в ChatGroq.bind_tools(),
а выполнение идёт через Client.call_tool(). Это реальное использование MCP,
а не прямой импорт файловых функций агентом.

Используется API SDK v2, а не старый mcp.server.fastmcp.FastMCP:
[официальная документация SDK](https://py.sdk.modelcontextprotocol.io/),
[исходный код SDK](https://github.com/modelcontextprotocol/python-sdk).
У MCP полевые имена Python в этой версии — input_schema, structured_content,
is_error. call_tool поддерживает и структурированный результат, и JSON в
единственном текстовом блоке: обычный dict в SDK может передаваться как текст.

## Описание каждого модуля и функции

### main.py

- **run(input_path, output_path, llm=None)**: запрещает одинаковый вход/выход,
  создаёт модель (или принимает тестовую), запускает сервер тем же Python,
  открывает одну MCP-сессию, обнаруживает read_article и получает количество
  статей. Создаёт граф и выполняет его один раз. Лимит шагов 6 × N + 3 учитывает
  до трёх попыток выбора и три обязательных узла на статью. cache=None отключает
  клиентское кеширование результатов MCP, чтобы запись не подменялась кешем.
- **describe_error(exc)**: разворачивает вложенные ExceptionGroup от асинхронного
  MCP, чтобы журнал содержал причину ошибки, а не только «TaskGroup failed».
- **main()**: загружает .env, читает --input/--output, создаёт logs/run.log,
  запускает run. Возвращает код 0 при успехе, 1 при ошибке, 130 при прерывании.

### src/graph.py

- **AgentState**: схема состояния total, next_index, selected_index, attempts,
  current_article, current_summary. В состоянии нет общей истории диалога.
- **call_tool(client, name, arguments=None)**: исполняет MCP-инструмент,
  проверяет is_error, извлекает dict из structured_content либо JSON-текста.
  Неожиданный формат завершает работу явной ошибкой.
- **build_graph(client, llm, read_schema)**: привязывает обнаруженный инструмент
  к модели, регистрирует перечисленные ниже узлы и возвращает скомпилированный граф.
- **initialize_node(state)**: получает count, вызывает prepare_results,
  записывает путь резервной копии в лог, обнуляет прогресс.
- **agent_node(state)**: передаёт модели компактное состояние и системный prompt.
  Принимает ровно один read_article с ожидаемым индексом. Неверный ответ
  повторяется через переход графа; третья неудача вызывает исключение.
- **read_node(state)**: читает одну статью через MCP в current_article.
- **summarize_node(state)**: вызывает summarize_article и сохраняет current_summary.
- **save_node(state)**: отправляет index и summary в MCP; сверяет count, увеличивает
  next_index и очищает временные поля только после успешной записи.
- **should_continue(state)**: направляет в END после всех записей, иначе в agent.
- **route_selection(state)**: направляет допустимый выбор в read, неверный — в agent.

### src/summarizer.py

- **create_llm()**: проверяет наличие GROQ_API_KEY, создаёт ChatGroq с температурой
  0, таймаутом 60 секунд, max_retries=2 и max_tokens=2048. Временные сетевые ошибки
  и поддерживаемые SDK ошибки API повторяются ограниченно. Постоянные ошибки
  авторизации/модели требуют исправления конфигурации.
- **summarize_article(llm, article)**: создаёт независимый запрос для одной статьи.
  Системная инструкция требует сохранить факты и не выполнять команды из текста.
  Пустой или обрезанный по лимиту ответ не сохраняется.

### mcp_server.py

- **create_server(input_path, output_path)**: запрещает совпадающие пути, заранее
  валидирует все статьи, создаёт MCPServer и регистрирует четыре инструмента.
  Пути задаёт CLI, модель не может передать произвольный путь.
- **get_articles_count()** (MCP tool): возвращает объект с count.
- **prepare_results()** (MCP tool): сохраняет старый выход и создаёт [].
  Повторный вызов в той же сессии не очищает результаты второй раз.
- **read_article(index)** (MCP tool): отдаёт только статью с указанным индексом.
- **append_result(index, summary)** (MCP tool): требует подготовки выхода, берёт
  id/title из исходной статьи и делегирует запись файловому модулю.
- **main()**: разбирает обязательные --input/--output и запускает stdio.
  Нельзя писать произвольный текст в stdout сервера: там MCP-протокол.

### src/file_tools.py

- **load_articles(file_path)**: читает JSON, в том числе UTF-8 с BOM, проверяет
  список, обязательные строки, уникальность id и размер каждой статьи.
- **atomic_write(file_path, data)**: создаёт папку при необходимости, сериализует
  JSON во временный файл рядом с выходом, делает flush/fsync и os.replace.
  При ошибке удаляет временный файл; предыдущий результат сохраняется.
- **prepare_results(file_path)**: копирует существующий выход в
  result.<UTC timestamp>.bak.json, затем атомарно создаёт пустой список.
- **get_articles_count(articles)**: возвращает длину проверенного списка.
- **read_article(articles, index)**: отвергает отрицательные индексы и выход за
  границы; возвращает одну запись.
- **append_result(file_path, article, summary)**: проверяет непустой summary,
  читает текущий результат, формирует id/title/summary, сохраняет атомарно.
  Повтор той же записи не создаёт дубликат; конфликт для того же id — ошибка.

## Сохранение, ошибки и ограничения

Каждый успешный save сразу обновляет корректный result.json. При ошибке
следующая статья не начинается; уже сохранённые записи остаются на диске.
При новом запуске прежний result.json сохраняется в резервную копию, затем
обработка начинается **с первой статьи**. Автоматического resume нет.
Не запускай два процесса с одним выходным файлом одновременно:
межпроцессная блокировка не реализована.

Логи содержат этап, номер статьи, итог и ошибки. Приложение специально не
логирует ключ, полный prompt и текст статьи. logs/run.log дополняется при
каждом запуске. При 401 проверь ключ; при 429 — лимиты Groq; после исчерпания
повторных попыток дождись восстановления лимита и перезапусти.
Если сервер не стартовал, его ошибка видна в stderr терминала.

До проверки ввода выход не изменяется. При недоступном Groq после подготовки
выхода может остаться [] или частичный результат; предыдущая версия лежит
в резервной копии. Изначальные исходники сохранены в backups/.

Резюме создаёт LLM, поэтому формальная корректность JSON не доказывает
идеальную полноту и точность содержания. Короткие плотные исходные статьи
могут сокращаться незначительно, поскольку prompt требует сохранять цифры
и исключения. Число обычных запросов к Groq — 2 × количество статей.

## Проверки

```powershell
.\.venv\Scripts\python.exe -m unittest discover -s tests -v
.\.venv\Scripts\python.exe -m pip check
.\.venv\Scripts\python.exe main.py
```

tests/test_workflow.py использует настоящий дочерний MCP-сервер и LangGraph,
но заменяет LLM на FakeModel, чтобы регрессионные проверки не требовали ключа
и не расходовали лимит API.

- **FakeModel.__init__ / bind_tools / ainvoke**: задают сценарий, принимают схему
  и возвращают контролируемые tool calls / резюме; могут имитировать ошибку.
- **WorkflowTests.setUp / execute**: создают временные вход/выход и запускают run.
- **test_full_graph_real_mcp_and_bounded_context**: все записи сохраняются,
  исходные id/title совпадают, сообщения не накапливаются, state очищается.
- **test_partial_result_survives_model_failure**: сбой на второй статье оставляет первую.
- **test_bad_agent_choice_is_bounded**: неверный выбор прекращается после трёх попыток.
- **test_empty_input_and_backup**: [] обрабатывается без LLM, старый результат сохранён.
- **test_invalid_source_keeps_previous_output**: некорректный вход не меняет выход.
- **test_missing_input_is_reported_before_starting_mcp**: отсутствующий файл получает понятную ошибку до запуска сервера.
- **test_same_path_is_rejected**: исходный файл нельзя перезаписать результатом.
- **test_atomic_failure_preserves_previous_result**: ошибка замены файла сохраняет старый JSON.
- **test_idempotent_save_and_validation**: повтор записи не дублируется,
  конфликт/отрицательный индекс/дублирующийся id отвергаются.
- **test_truncated_summary_is_rejected**: обрезанный ответ не считается успешным.

Результат проверки 19 октября 2026 года: реальный Groq end-to-end успешно
обработал 10/10 статей из data/test_articles.json и создал data/result.json.
Все 10 регрессионных тестов прошли, pip check не выявил конфликтов зависимостей.
