# Vanilla RAG для корпоративной базы знаний

## Описание проекта

В проекте реализован базовый RAG-pipeline для ответов на вопросы по внутренней корпоративной базе знаний.

Цель работы — сравнить качество ответов языковых моделей без доступа к корпоративным документам и после добавления retrieval-контекста.

В качестве данных используются:

- 10 корпоративных статей;
- 50 вопросов;
- 50 эталонных ответов.

Вопросы и эталонные ответы объединяются по `id` в единый `golden_set`.

## Zero-shot baseline

Сначала оцениваются две модели без RAG, то есть модели получают только текст вопроса и не имеют доступа к корпоративным статьям.

Через Groq API используется модель:

```text
openai/gpt-oss-120b
```

В качестве локальной модели используется:

```text
Qwen/Qwen2.5-0.5B-Instruct
```

Локальная модель запускается через `vLLM`.

Для обеих моделей ответы оцениваются с помощью:

- BLEU;
- ROUGE;
- LLM-as-a-judge.

Judge сравнивает ответ модели с эталонным ответом и выставляет оценку:

```text
0 — неверно
1 — частично верно
2 — полностью верно
```

Результаты zero-shot:

| Модель | BLEU | ROUGE-1 | ROUGE-2 | ROUGE-L | Judge |
|---|---:|---:|---:|---:|---:|
| Groq | 1.62 | 0.144 | 0.052 | 0.139 | 0.08 |
| Qwen2.5-0.5B | 3.83 | 0.158 | 0.044 | 0.153 | 0.06 |

Обе модели показывают очень низкую фактическую корректность, что ожидаемо: вопросы относятся к внутренним корпоративным данным, которых модели не знают.

## Подготовка документов для RAG

Корпоративные статьи преобразуются в LangChain `Document`.

В `page_content` объединяются:

```text
title + text
```

`id` и `title` сохраняются в metadata.

Поскольку статьи короткие — примерно 730–870 символов — дополнительный chunking не используется:

```text
1 статья = 1 chunk
```

## Embeddings

Для построения векторных представлений используется:

```text
sentence-transformers/paraphrase-multilingual-MiniLM-L12-v2
```

Embeddings вычисляются через `HuggingFaceEmbeddings` на GPU и нормализуются:

```python
normalize_embeddings=True
```

## Векторный поиск

Для хранения и поиска векторов используется FAISS.

Индекс создаётся непосредственно из LangChain `Document`:

```text
Documents
→ HuggingFace embeddings
→ FAISS
```

Для каждого вопроса выполняется similarity search.

В финальной версии retrieval используется:

```text
k = 2
```

## Оценка retriever

Для тестового набора заранее известно, к какой статье относится каждый вопрос. Это используется как ground truth для оценки retrieval.

Получены:

```text
Recall@1 = 0.78
Recall@2 = 0.92
Recall@3 = 0.92
```

То есть в 78% случаев правильная статья находится на первом месте, а в 92% — входит в первые два найденных документа.

## RAG generation

Для каждого вопроса выполняется следующий pipeline:

```text
вопрос
↓
FAISS similarity search
↓
top-2 документа
↓
объединение их текста в context
↓
Groq LLM
↓
ответ
```

Модель получает prompt с найденным контекстом и инструкцией отвечать только на его основе.

Для генерации используется та же модель:

```text
openai/gpt-oss-120b
```

Это позволяет корректно сравнивать одну и ту же LLM:

```text
без RAG
vs
с RAG
```

## Результаты RAG

| Режим | BLEU | ROUGE-1 | ROUGE-2 | ROUGE-L | LLM-as-a-judge |
|---|---:|---:|---:|---:|---:|
| Groq zero-shot | 1.62 | 0.144 | 0.052 | 0.139 | 0.08 |
| Local Qwen zero-shot | 3.83 | 0.158 | 0.044 | 0.153 | 0.06 |
| **Groq + RAG** | **30.47** | **0.767** | **0.301** | **0.759** | **1.74** |

## Вывод

Zero-shot модели практически не способны надёжно отвечать на вопросы по закрытой корпоративной базе знаний.

После добавления RAG качество существенно выросло:

```text
BLEU: 1.62 → 30.47
ROUGE-L: 0.139 → 0.759
Judge: 0.08 → 1.74
```

Основной прирост качества связан не с заменой LLM, а с добавлением релевантного корпоративного контекста.

При этом итоговое качество напрямую зависит от retrieval: если нужный документ не попадает в найденный контекст, генератор не получает необходимые данные для правильного ответа.
